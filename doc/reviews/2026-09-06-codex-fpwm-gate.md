## FINDINGS

1. **P0 — (a) arithmetic/unit error: the disengagement threshold is on the destructive side of zero current.**  
   [`fpwmDropDuty = dZero - err - margin`](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:1499>) keeps complementary PWM active *below* the zero-current duty; the comparison at [src/buck.h:1520](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:1520) therefore disengages only after reverse current already exists. For the stated buck, `r=27/68`, `err≈0.00794`, margin `0.01`, so drop is about `0.379`, versus zero current at `0.397`. That permits roughly `(0.397−0.379)·68/0.03 ≈ 41 A` reverse current before measurement errors or sampling overshoot. Boost has the same unsafe direction because its current is also proportional to `D−dZero`. This directly falsifies the no-reverse-current down-ramp claims in [Configuration.md:404](/Users/fab/dev/pv/fugu-mppt-firmware/doc/Configuration.md:404>) and [Power Loop.md:85](/Users/fab/dev/pv/fugu-mppt-firmware/doc/Power Loop.md:85>).

2. **P0 — (c) real design defect: the gate is checked before, not against, the duty that is about to be committed.**  
   `protect()` evaluates the gate at [src/mppt.h:750](/Users/fab/dev/pv/fugu-mppt-firmware/src/mppt.h:750), then the control update changes duty later at [src/main.cpp:1023](/Users/fab/dev/pv/fugu-mppt-firmware/src/main.cpp:1023) or [src/main.cpp:1026](/Users/fab/dev/pv/fugu-mppt-firmware/src/main.cpp:1026). Manual mode can overshoot by one ramp step; automatic control allows a negative perturbation as large as the entire present duty at [src/mppt.cpp:273](/Users/fab/dev/pv/fugu-mppt-firmware/src/mppt.cpp:273). `pwmPerturb()` then sees the old engaged state and immediately computes/commits a CCM complementary window at the new duty ([src/buck.h:1267](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:1267), [src/buck.h:1282](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:1282), [src/buck.h:1306](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:1306)). Thus even a corrected drop threshold can be crossed for one full control interval with the rectifier still complementary.

3. **P0 — (c) real design defect: the filter-settling freeze covers only manual PWM, not the automatic modes using the gated boost configurations.**  
   The safety argument explicitly depends on freezing duty while `fpwmGateCnt` advances ([src/buck.h:139](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:139)), but the only freeze is in `updateManual()` at [src/mppt.cpp:355](/Users/fab/dev/pv/fugu-mppt-firmware/src/mppt.cpp:355). Normal MPPT, sweep, PSU and PV control continue perturbing at [src/mppt.cpp:273](/Users/fab/dev/pv/fugu-mppt-firmware/src/mppt.cpp:273). Consequently, the counter can reach 192 while duty and the bus are still moving and the EWMA ratio remains stale—the exact early-engagement mechanism the hold was meant to remove. This affects the default-gated `fboost` and `fboost_pv`; the latter explicitly runs `mode=pv` at [converter.conf:11](/Users/fab/dev/pv/fugu-mppt-firmware/config/lab/fboost_pv/conf/converter.conf:11).

4. **P1 — (c) real design defect: a protection trip while arming can permanently deadlock a manual restart.**  
   If `fpwmGateCnt>0`, an early protection path can call `disable()` before the next gate update. `disable()` clears `fpwmEngaged` and bumps the epoch but does not clear the RT-owned counter ([src/buck.h:1343](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:1343)). While disabled, main deliberately skips `protect()` and hence `updateForcedPwmGate()` ([src/main.cpp:1013](/Users/fab/dev/pv/fugu-mppt-firmware/src/main.cpp:1013)). After backoff, a nonzero manual target produces a positive step, but stale `fpwmGateCnt>0` makes `forcedPwmGateArming()` true and [src/mppt.cpp:355](/Users/fab/dev/pv/fugu-mppt-firmware/src/mppt.cpp:355) returns without enabling the converter. The epoch is never consumed, so this repeats indefinitely. Frequency rescaling does not clear that state either.

5. **P1 — (c) real design defect: the cross-core protocol still contains data races and is not a coherent multi-publisher transaction.**  
   `forcedPwm` is plain memory written by core 0 at [src/buck.h:572](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:572), but RT protection reads it through `forcedPwm_()` at [src/mppt.h:650](/Users/fab/dev/pv/fugu-mppt-firmware/src/mppt.h:650), before the acquire load in `updateForcedPwmGate()`. The later release/acquire cannot legalize that earlier conflicting access. Conversely, bare `sync` reads RT-written `fpwmUngated`, `fpwmGateCnt`, and `fpwmEngageDuty` through [src/cli.cpp:119](/Users/fab/dev/pv/fugu-mppt-firmware/src/cli.cpp:119)–126; those fields are non-atomic.

   There is also a concrete mismatched-payload interleaving: RT `disable()` stores `fpwmImmediateReq=false` and is preempted before its epoch increment; core 0 publishes `sync forced!` and increments epoch E1; RT resumes and increments E2. The consumer sees E2 but the current `immediate=true`, and re-latches `fpwmUngated`, defeating `disable()`’s stated requirement that a restart re-earn forced PWM. Relaxed access to `fpwmEngaged` alone is adequate for that standalone flag; the problem is the plain shared fields and the two publishers sharing an epoch without an atomic payload.

6. **P2 — (c) real design defect: `forced!` can report “ungated” without making the stationary waveform complementary.**  
   The override latches engaged and bypasses gate evaluation at [src/buck.h:1509](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:1509)–1515, but the new stationary-duty fade still requires `dutyCtrlEff() > fpwmDropDuty` at [src/buck.h:1549](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:1549). With an invalid ratio or a fixed duty below drop, the LS remains at its diode-emulation minimum forever while status says `on (ungated)`. That contradicts the advertised gate-bypassing behavior in [Console.md:130](/Users/fab/dev/pv/fugu-mppt-firmware/doc/Console.md:130).

7. **P2 — (c) real design defect: the new RT gate-transition logs allocate.**  
   Both transition paths call `UART_LOG` from `protect()`’s RT path at [src/buck.h:1524](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:1524) and [src/buck.h:1530](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:1530). With deferred logging enabled, `UART_LOG` reaches `enqueue_log()`, which executes `new char[...]` at [src/logging.cpp:124](/Users/fab/dev/pv/fugu-mppt-firmware/src/logging.cpp:124). With deferral disabled it takes the synchronous formatting/output path instead. Either violates the stated no-allocation/no-blocking RT rule.

8. **P2 — (a) arithmetic/unit error: `fpwm_gate_hold` silently wraps before validation.**  
   [src/buck.h:1081](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:1081) applies only a lower bound and then narrows `long` to `uint16_t`. A configured value of 65536 becomes zero, so the first `++fpwmGateCnt < fpwmGateHold` test fails and forced PWM engages immediately. Reject or saturate values above 65535.

9. **P3 — (a) arithmetic/unit error: `2%·r` is not the exact worst-case buck ratio error promised by the documentation.**  
   For independent ±1% multiplicative sensor errors, the buck’s upper ratio factor is `1.01/0.99 = 1.020202…`, not `1.02`. At `r=0.4`, [src/buck.h:1492](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:1492) understates the bound by `8.08×10⁻⁵` duty, about 0.18 A under the supplied 68 V/30 mΩ assumptions. The default 0.01 margin dominates it, but margin zero is accepted. For boost, `0.02·r` is slightly conservative; importantly, scaling by `r`, rather than boost `dZero=1−r`, is correct.

10. **P3 — (a) arithmetic/unit error in the contract comment: the `dutyCtrlEff()` prose states the dead-time effect backwards.**  
    [src/buck.h:1451](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:1451) says ctrl turn-on is delayed and realized duty is smaller. The configured one-tick FED delays `genHS_`’s falling edge, lengthening its high pulse. The implementation comment immediately below correctly says this; the stale Doxygen description should not remain as an opposing safety argument.

## SURVIVED

- `dutyCtrlEff()`’s executable expression survives. MCPWM `genHS_` is high from TEZ to `cmpHS`; IDF routes its one-tick negative-edge delay to FED, which delays the falling edge ([local IDF `mcpwm_gen.c`:314](/Users/fab/dev/esp/idf5.5/components/esp_driver_mcpwm/src/mcpwm_gen.c:314>)). Therefore realized ctrl duty is approximately `(pwmCtrl+1)/period`, while the code returns `pwmCtrl/period`: an underestimate of one tick, safe for both engagement and disengagement. In boost, `pinCtrl` is physical `pwm_li` ([src/buck.h:1134](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:1134)); it is still logical `genHS_`, and `pwmCtrl`/`cmpHS` is its on-count ([src/pwm/mcpwm.h:168](/Users/fab/dev/pv/fugu-mppt-firmware/src/pwm/mcpwm.h:168), [src/buck.h:420](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:420)). The denominator correctly restores the timer period by adding the software-reserved `dtLh`.

- The core zero-duty arithmetic survives apart from the findings above: `vh/vl` selection, `dZero=r` for buck, `dZero=1−r` for boost, the `vh>vl` guard, and using `r·error` in both topologies are directionally correct. The `max(0,…)` is redundant once `vh>vl` holds, but harmless.

- Leaving `fpwm_gate` enabled by default for `fboost` and `fboost_pv` is correct. At pre-charge `Vout≈Vin`, the strict `vh>vl` test refuses forced PWM; the physical boost HS rectifier remains diode-emulating while physical LS duty raises `Vout`, after which a valid ratio becomes measurable. Setting `fpwm_gate=0` there would reintroduce the destructive duty-from-zero behavior. The automatic-ramp omission is the implementation defect, not those configuration defaults.

- The new LS fade cannot exceed the complementary limit: [src/buck.h:1255](/Users/fab/dev/pv/fugu-mppt-firmware/src/buck.h:1255)–1257 ensures `pwmCtrl+pwmRect ≤ driverPwmMax−1 < period`. The fade clamps to that maximum, so it cannot produce `cmpLS >= period` or remove the reserved wrap dead-time. `fpwmFadeHold` is decremented once on every applicable automatic update after the mutually exclusive clamp/fade chain. It is skipped by the explicit manual-LS early return and when protection exits before calling this function, but fade is inactive on those paths. A value of 256 has the protective sign; no evidence establishes it as optimal, but it does not create shoot-through or double-decrement.

- Both REQUEST predicates are appropriate for the stated rig contract. `enableSyncRect()` must honor the request so an untrustworthy zero-current sensor does not disable all bounded synchronous conduction throughout the hold; using only the gated state would force the forward current through the body diode during those samples. The `Vr-sensor-fail` branch likewise needs REQUEST because sensor trust does not improve while the physical gate is armed: for example, `getDutyCycle=0.6`, `vr=0.45`, and `iOutSmall=true` trips the strict `0.8D` branch but not the forced-mode `0.5D` branch. This relies on the stated assumption that requesting forced PWM denotes an unusable current sensor.
